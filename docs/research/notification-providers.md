# Free development environments for Cadence notifications

Researched: 2026-11-12. Context: [Which notification services offer a suitable free development environment?](https://github.com/ilyas0v/software-factory-project/issues/3), part of [Cadence in-app notifications — decision map](https://github.com/ilyas0v/software-factory-project/issues/1).

## Finding

Knock, Novu Cloud, and Courier all offer an ongoing free plan with a separate environment suitable for testing a real hosted in-app inbox. None provides unlimited free delivery simply because requests target development. Keep all three on the shortlist; the tradeoffs below need a human provider decision, especially retention, initial catalogue size, production budget, and branding. This research does **not** select a provider. The official free-plan and environment evidence is detailed below.

For this comparison, a **free development environment** means isolated test data/configuration and credentials, usable with the hosted feed on an ongoing free plan. A **free production tier** is a no-charge usage allowance that can also serve production; it does not by itself prove isolation. A **trial** expires or temporarily grants paid features. A preview that never creates a real subscriber feed cannot validate persistence, identity, or cross-session state.

Only public documentation and repository files were inspected. No account was created, service provisioned, dependency installed, notification sent, or database opened. Pricing and entitlements should be rechecked at setup; account-specific limits and runtime behavior were not verified hands-on.

## Cadence context

The [README](../../README.md) names Knock as a future signup, not an architectural commitment. [package.json](../../package.json) has React 19, React Router 8 with SSR, and no notification SDK. [The schema](../../app/db/schema.ts) supplies numeric person IDs but no notification feed tables. [The app layout](../../app/routes/layout.app.tsx) loads the current person and renders the sidebar, DevUI, and transient Sonner toasts. [The session helper](../../app/lib/session.ts) reads the current ID from a cookie; the DevUI can change it. These are integration entry points, not evidence that a feed is already implemented.

Use [the glossary](../../GLOSSARY.md): Student, Instructor, Platform Admin, and Team Admin. A person may have team responsibilities alongside their platform role. Discussions, Refund Requests, Purchases, Enrollment, course changes, and Seats are possible event sources; provider capability does not approve any of them as notification types.

## Backend triggers and duplicate events

| Provider | Server contract | Retry/deduplication contract |
| --- | --- | --- |
| Knock | Direct workflow trigger API; workflow identifies recipients and can carry actor, tenant, and event data. [Triggers](https://docs.knock.app/send-notifications/triggering-workflows/overview), [API](https://docs.knock.app/api-reference/overview) | `Idempotency-Key` on workflow-trigger POST only; default 24-hour window, up to 255 characters. Only successful responses are cached; mismatched parameters fail. [API idempotency](https://docs.knock.app/api-reference/overview) |
| Novu | Server API/SDK triggers a workflow ID for subscriber(s) with payload; do not expose its secret key to the client. [Trigger workflow](https://docs.novu.co/platform/workflow/trigger-workflow) | `Idempotency-Key` for API-key-authenticated POST/PATCH. **Not enabled for every organization: contact support first.** Success/error responses cache for 24 hours; in-progress duplicates return 409. `transactionId` does not supply equivalent API-boundary deduplication or billing protection. [Idempotency](https://docs.novu.co/api-reference/idempotency) |
| Courier | Server `POST /send`/Node `client.send.message`, with recipient `user_id`, template or content/data, and `inbox` routing. Acceptance returns a request ID; it is not proof of feed delivery. [Send API](https://www.courier.com/docs/api-reference/send/send-a-message), [React example](https://www.courier.com/docs/guides/add-an-inbox-to-react) | Send API accepts `Idempotency-Key`, scoped to endpoint, replaying the original response including errors. Default 25-hour lifetime; `x-idempotency-expiration` can extend to at most one year. [Send API](https://www.courier.com/docs/api-reference/send/send-a-message) |

**Cadence integration implications, not selected architecture:**

- Resolve recipients and authorization from committed Cadence domain state on the server. Providers do not decide whether a Student may still open a course, whether a Seat can be claimed, or who may decide a Refund Request. A notification link must recheck current authorization.
- Use a stable string derived from `users.id` consistently for profile creation, triggering, feed authentication, and tests. Keep environment data separate: the [seed script](../../scripts/seed.ts) recreates tables, so local IDs can be reused after reseeding. Decide a reset or test-identity convention before real testing so old provider history does not attach to a different seeded person.
- Issue feed credentials from the existing authenticated session, never an arbitrary user ID supplied by the browser. On switch-user/logout, clear previous feed state and connection before authenticating the next person. Prove that one person's credentials cannot retrieve another person's feed, including direct API calls.
- Choose a stable event/recipient key and preserve it across retries; do not create a fresh key per attempt. Provider idempotency windows do not ensure durable exactly-once notification creation. Decide how Cadence records successful domain changes and retries failed notification delivery after commit; never send before a transaction that might roll back.
- Define the minimal payload: event type/ID, actor, recipient, resource reference, safe copy, and internal destination. Avoid copying full discussion text or refund reasons into the provider by default. Choose retention/deletion responsibilities and what happens when the destination disappears.

These billing units are not interchangeable. For a purely in-app event sent once to 100 recipients, expect roughly 100 delivered messages (Knock), 100 subscriber workflow runs (Novu), or 100 sends (Courier), subject to filtering and the billing rules above. Adding email changes Knock's message count, while the cited Novu/Courier units can cover more than one channel. This is a worked inference from metering rules, not an approval to change Cadence's existing email behavior.

Region may also affect selection: Novu lists US/EU hosting on Free. [Pricing](https://www.novu.co/pricing/) Knock's current account documentation still describes EU residency as planned for the end of 2026, so availability must not be assumed. [Plans](https://docs.knock.app/manage-your-account/knock-plans) Courier lists EU residency with Business. [Pricing](https://www.courier.com/pricing) No region or data-handling policy has been chosen for Cadence by this research.

## Decision handoff and remaining evidence

Recommended shortlist: **Knock and Novu Cloud as the primary comparison, with Courier retained as a credible third option.** Knock has the existing README context, broad free workflow capacity, and unlimited documented feed retention. Novu has a smaller paid entry point, explicit Dev/Prod setup, React 19 support, and a free usage hard stop, but requires deliberate handling of five-workflow/30-day limits and idempotency enablement. Courier offers real Test Inbox delivery, flexible isolated environments, and documented persistence without expiry, with a different paid billing transition. These are reasons to compare, not a provider selection.

The human decision should settle:

1. **What does persistent mean?** Survives reload/login, 30/90 days, or indefinite history? Should old links persist after Enrollment ends or a discussion is deleted?
2. **How large is the initial catalogue?** Map approved events to workflows and recipient fan-out before judging whether Novu Free is enough.
3. **What are the approved attention semantics?** Unseen versus unread badge, when read/seen changes, mark-all behavior, archive/dismiss, and cross-device expectations.
4. **Which preferences and team boundaries exist?** Personal opt-outs, required operational notices, team-specific defaults, and whether a Team Admin controls others' preferences. Team Licence support alone does not imply provider multi-tenancy.
5. **What budget, branding, region, and deletion obligations apply?** Evaluate the first paid tier and shared test quota, not only the starting price.
6. **What delivery guarantee is required?** Failure recovery, retry horizon, permanent deduplication, and whether an outage may delay a notice while the underlying domain action succeeds.

Suggested decision tickets if these are not already covered: “What notification history must Cadence retain?”, “What delivery and duplicate-prevention guarantees must Cadence provide?”, and “Which service fits the approved catalogue and operating budget?” Keep human choices separate from this factual research resolution.

Before implementation sign-off, an authorized validation task should confirm the selected account's ongoing Free entitlement after any trial, card status, isolated real test feed, quota visibility/boundary behavior, provider-specific idempotency availability, session/user-switch isolation, read-state persistence, realtime reconnect, retention/expiry, and React Router SSR behavior. The present task did not authorize provisioning or notification delivery, so no live verification was attempted.
